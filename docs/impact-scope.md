# 수정 전 영향 범위 파악

`AGENTS.md` 8번의 상세 체크리스트. 코드를 수정하거나 추가하기 전, 다음을 확인한다.

## 작업 전: 도메인 문서 확인

- 레포에 `CONTEXT.md`/`CONTEXT-MAP.md` 또는 ADR(`docs/adr/` 등)이 있으면 손대는 영역을 먼저 읽는다. 명명·용어는 프로젝트 도메인 용어집(ubiquitous language)을 일관되게 쓰고, 임의로 동의어를 만들지 않는다. 기존 ADR 결정을 존중하며, 어긋나야 하면 아래 원칙(보고 후 결정)을 따른다.
- 용어집이 없는데 새 기능·새 도메인을 다루는 작업이면, 용어집 작성을 먼저 우선한다.
- 단, 단일 파일 수정·버그 픽스 등 소규모 작업은 예외다(`AGENTS.md` 2번 단순성 — 불필요한 오버헤드 금지).

## 기존 코드 수정 시

- 함수/메서드의 시그니처를 변경할 때는 호출부를 모두 확인한다.
- 공통 모듈(유틸, 상수, 타입, 인터페이스)을 수정할 때는 사용처를 파악한다.
- 변경 범위가 예상보다 넓다면 진행 전 사용자에게 보고하고 방향을 확인한다.

## 신규 코드 추가 시

- 유사한 기능이 코드베이스에 이미 존재하는지 검색한다(검색어: 도메인 용어, 함수명 후보, 관련 키워드).
- 존재한다면 재사용, 확장, 신규 작성 중 어느 쪽이 적절한지 판단하고 그 근거를 밝힌다.
- 기존 코드의 패턴(레이어 구조, 명명 규칙, 에러 처리 방식)을 먼저 파악하고 일관성을 따른다.
- 단, **기존 패턴이 best practice / 언어·프레임워크 공식 권장 방식과 어긋난다고 판단되면 그대로 추종하지 않는다.** 차이와 트레이드오프를 보고하고 결정을 받는다.
  - "같은 모듈에 비표준 선례가 있다"는 사실 자체는 그 선례를 따를 정당한 사유가 아니다.
  - **발견 시 최우선은 사용자에게 보고하는 것이다.** 정정 여부와 시점(같은 작업에 포함 / 별도 작업으로 분리 / 정정하지 않음)은 사용자가 결정한다.
  - 사용자 결정 없이 기존 비표준 선례를 *직접 수정하지 않는다*(`AGENTS.md` 3번 정밀한 수정 원칙).
  - 판단 기준: "이 패턴이 공식 문서 / 표준 가이드 / 해당 분야 best practice와 어긋나는가?" → 어긋난다면 일단 보고.

## 새 의존성 추가 시

- 같은 역할을 하는 라이브러리가 이미 프로젝트에 있는지 확인한다.
- 추가가 필요한 이유, 대안, 영향(번들 크기, 라이선스, 유지보수 상태)을 보고하고 사용자의 승인을 받는다.

## 원칙

코드베이스 탐색에 5분을 쓰는 것이 잘못된 가정으로 30분 작업한 것을 되돌리는 것보다 항상 싸다.
