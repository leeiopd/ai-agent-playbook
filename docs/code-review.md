# 코드 리뷰 모드

`AGENTS.md` 10번에서 가리키는 전체 절차. 다음 키워드 중 하나가 포함되면 리뷰 모드로 진입한다: `리뷰`, `review`, `코드 리뷰`, `PR 리뷰`. 일반 구현 작업에는 적용하지 않는다.

## 실행 환경

리뷰 모드 진입 시 **워크트리(worktree)를 생성하여 리뷰를 진행한다** (git worktree를 지원하는 도구에서).

워크트리 생성 절차:

1. 현재 브랜치와 리뷰 대상 브랜치를 확인한다 (`git branch --show-current`).
2. 리뷰 대상 브랜치를 원격에서 최신화한다.
   - 현재 브랜치 ≠ 리뷰 브랜치: `git fetch origin BRANCH:BRANCH` (로컬 브랜치를 원격 기준으로 직접 업데이트)
   - 현재 브랜치 = 리뷰 브랜치: `git pull --ff-only` (현재 브랜치 fast-forward 업데이트)
3. 메인 워크트리를 기본 브랜치(dev 등)로 전환한다: `git checkout dev` (이미 dev라면 스킵)
4. 리뷰 대상 브랜치를 워크트리로 생성한다. 프로젝트 루트의 별도 작업 디렉토리(예: `.worktrees/`)에 생성한다:
   `git worktree add .worktrees/review-BRANCH BRANCH`
5. 워크트리 디렉토리에서 diff·파일 탐색을 수행한다.
6. 워크트리 안에서는 파일을 읽기만 한다. 직접 수정하지 않는다.
7. 리뷰 결과를 출력한 후 "리뷰가 끝났습니까?" 라고 사용자에게 확인한다. 사용자가 끝났다고 응답하면 `git worktree remove` 로 워크트리를 정리한다.
8. 이미 워크트리가 존재하거나 사용자가 "워크트리 없이 진행해"라고 지시하면 생략 가능하다.

## 검토 범위

기본값은 **현재 브랜치와 기본 브랜치(main/master/develop) 간의 diff**다. 사용자가 다른 범위(특정 커밋, 특정 파일, 특정 라인)를 지정하면 그에 따른다.

## 행동 제약

리뷰 모드에서는 **발견 사항을 보고만 한다**. 직접 수정하거나 커밋하지 않는다. 사용자가 별도로 "수정해라"라고 지시한 경우에만 수정 작업으로 전환한다.

## 검토 기준: 엔터프라이즈급 서비스를 운영하는 10년차 실무 개발자 수준

다음 10개 카테고리를 모두 스캔한다. 변경과 무관한 카테고리는 "해당 없음"으로 명시한다. 변경 규모가 작고(예: 10줄 이하) "해당 없음" 항목이 다수인 경우, "해당 없음" 항목은 한 줄로 묶어 보고한다.

1. **사이드 이펙트 / 영향 범위**: 변경된 함수·인터페이스의 호출부, 공유 상태, 트랜잭션 경계, 캐시 무효화
2. **동시성 / 경쟁 조건**: 락, 트랜잭션 격리 수준, 비동기 처리 순서, idempotency
3. **장애 / 복원력**: 외부 의존성 실패 시 동작, 타임아웃, 재시도, 부분 실패, rollback 가능성
4. **데이터 정합성**: 마이그레이션 호환성, 읽기/쓰기 모델 동기화, 이벤트 순서, Outbox 등 패턴 위반
5. **보안**: 인증/인가 우회, 입력 검증, injection, PII 노출, 권한 escalation
6. **성능**: N+1 쿼리, 불필요한 fetch, 인덱스 미사용, 동기 호출 블로킹, 메모리 누수
7. **관측 가능성**: 로깅 누락, 메트릭, traceId 전파, 에러 컨텍스트
8. **계약 / 호환성**: API 하위 호환성, DB 스키마 backward/forward compatibility, 이벤트 schema evolution
9. **테스트**: 커버리지가 아닌 *시나리오* — 실패 경로, 경계값, 회귀 가능성
10. **운영**: 배포 순서 의존성, feature flag, 롤백 전략

## 심각도 분류

- **Blocker**: 머지하면 안 됨. 프로덕션 사고 직결, 데이터 손상/유실, 보안 취약점, 명백한 회귀.
- **Major**: 머지 전 수정 필요. 정합성·성능·호환성에 실질적 영향, 시간 내 발견되지 않으면 사고로 전이 가능.
- **Minor**: 머지 가능하나 후속 개선 권장. 잠재적 리스크, 가독성·유지보수성 저해.
- **Nit**: 취향·스타일 차원. 작성자 판단에 위임.

## 확신도 표기

각 발견 사항에 다음 중 하나를 표기한다:

- **확인됨**: 코드를 읽어 단정할 수 있는 사항.
- **추정**: 호출 맥락이나 운영 환경에 따라 달라질 수 있는 사항. 가정을 함께 명시한다.
- **질문**: 코드만으로 판단 불가, 작성자 확인이 필요한 사항.

## 코드베이스 일관성 검토

위 10개 카테고리와 별도로, 다음을 검토한다.

비교 대상은 다음 순서로 선정한다:

1. 같은 레이어의 다른 파일들 (예: 다른 Controller, 다른 Repository, 다른 Service)
2. 같은 디렉토리의 파일들

검토 항목:

- **컨벤션/스타일 차이**: 변경된 코드가 주변 코드와 명명 규칙, 에러 처리 방식, 레이어 경계, 의존성 방향 등에서 다른 경우 차이를 명시한다.
- **현대화 필요성**: 변경된 코드와 주변 코드가 모두 일관되더라도, 기존 패턴이 다음 중 하나에 해당하면 알린다:
  - 공식적으로 deprecated된 API/패턴
  - 해당 언어/프레임워크 메이저 버전에서 표준으로 권장하는 방식이 따로 있음
  - 보안·성능·정합성에서 측정 가능한 차이가 있음

단순히 "더 트렌디한 패턴"이라는 이유로는 제안하지 않는다.

이 섹션의 발견은 **결정이 아니라 정보 제공**이다. "고쳐야 한다"가 아니라 "사실 + 차이 + 트레이드오프"를 제시하고 사용자가 결정하도록 한다.

## Spec 충실도 검토 (원 이슈/스펙이 있는 경우)

위 10개 카테고리·일관성과 **별도 축**으로, 변경의 발단이 된 이슈/스펙/PRD를 기준으로 확인한다:

- **누락**: 스펙이 요구했으나 빠지거나 부분 구현된 것
- **스코프 크립**: 요청되지 않았는데 추가된 동작
- **오구현**: 구현된 듯하나 스펙과 다르게 동작하는 것

각 발견에 스펙의 해당 부분을 인용한다. 스펙이 없으면 "스펙 없음"으로 명시하고 이 축은 건너뛴다. **Standards(카테고리·일관성)와 Spec은 별개 축이므로 축을 가로질러 재랭킹하지 않는다** — 한 축의 통과가 다른 축의 실패를 가리지 않도록 따로 보고한다.

## 저장

리뷰 결과는 채팅 출력으로만 제공하는 것이 기본이다. 사용자가 "파일로 저장해줘" 등을 명시하면 그때 파일로 저장한다.
